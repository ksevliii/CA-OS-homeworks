# ИДЗ3: Морской грузовой порт (вариант 42)

Бусыгина Ксения, БПИ253

Консольная имитация работы грузового порта на языке C для Linux. Суда, диспетчер, буксиры, причалы, краны и склад представлены отдельными процессами. Реализованы четыре схемы взаимодействия для разных уровней оценки.

## Условие и сценарий работы

Судну нужны буксир для входа и выхода, совместимый причал и один или несколько совместимых кранов. Для разгрузки требуется свободное место на складе, для погрузки - запас нужного груза. Вместимость и число ресурсов ограничены.

Диспетчер организует прибытие, вход, швартовку, грузовую операцию и выход. Он меняет общее состояние модели; остальные процессы выполняют задания и возвращают подтверждения.

| Участник | Что делает в своём процессе |
|---|---|
| Судно | Ожидает прибытия и подтверждает завершение своего жизненного цикла |
| Диспетчер | Ведёт модельное время, выбирает суда, назначает ресурсы, проверяет ограничения |
| Буксир | Выполняет вход или выход назначенного судна |
| Причал | Выполняет швартовку и освобождение, хранит номер своего судна |
| Кран | Участвует в обработке грузовой порции и подтверждает её завершение |
| Склад | Рассчитывает вывоз и подвоз груза с учётом запасов, резервов и вместимости |

Всего работает `число судов + буксиров + причалов + кранов + 2` процессов, включая склад и диспетчер. В `examples/manual.txt` это шесть процессов: диспетчер и пять участников.

### Жизненный цикл судна

```text
прибытие -> ожидание входа -> вход с буксиром -> ожидание причала
-> швартовка -> грузовые порции -> ожидание выхода -> выход с буксиром -> отход
```

- Если складская порция недоступна, судно ждёт без занятого причала. 
- При ожидании после частичной обработки оно сначала освобождает причал и переходит во внутреннюю зону ожидания, затем снова швартуется. Состояние DEPARTED не устанавливается. 
- Освобождение и повторная швартовка подтверждаются процессом причала. Их длительность задаёт moorTime. 
- Для пересечения границы порта при входе и окончательном выходе по-прежнему нужен буксир. 
- Вместимость внутренней зоны ожидания отдельно не моделируется.

### Стратегии и предотвращение взаимного ожидания

`strategy` определяет порядок рассмотрения:

- `0` - меньший номер судна;
- `1` - более раннее прибытие;
- `2` - меньший остаток груза.

При равенстве выбирается меньший номер. Начатая операция не вытесняется; неподходящий сейчас запрос может быть пропущен ради следующего.

`reservation` задаёт выделение ресурсов:

- `0` - по стадиям: входной буксир, затем причал, затем грузовая операция;
- `1` - входной буксир и причал резервируются согласованно. Если складская порция недоступна, вход с резервированием откладывается. При изменении склада во время входа неиспользованный резерв причала отменяется.

В обоих режимах полный набор кранов и складская порция выделяются вместе. Буксир после входа освобождается. Краны не удерживаются в ожидании склада.

Дополнительно нельзя удерживать причал, ожидая груз, который должно привезти другое судно. Поэтому ожидающее склад судно освобождает причал.

Отсутствие подходящих ресурсов вообще, запрещённый тип груза или отключённый необходимый подвоз/вывоз могут сделать конфигурацию невыполнимой. Тогда моделирование заканчивается по времени или сигналу пользователя.

## Подготовка и сборка

Во всех следующих командах текущая директория - корень проекта. Сначала нужно собрать все программы командой make. Сценарий manual.txt одинаков для четырёх режимов, чтобы сравнивать способы взаимодействия.

## Запуск для каждой оценки

### 1. На 4-5: дочерние процессы, именованные семафоры и общая память

Один терминал:

```bash
./port_fork_named examples/manual.txt 100
```

Диспетчер сам вызывает fork и создаёт участников. Команды и ответы передаются через POSIX-разделяемую память, уведомления - через именованные POSIX-семафоры. В терминале видны события всех стадий и итог. После завершения родитель забирает дочерние процессы и удаляет созданные объекты.

### 2. На 6: дочерние процессы и неименованные семафоры

Один терминал:

```bash
./port_fork_unnamed examples/manual.txt 100
```

Родитель также создаёт участников через fork. Отличие - sem_init с pshared=1 вместо sem_open: сами неименованные семафоры размещены в общей памяти. Это второй вариант синхронизации, предыдущая программа при этом остаётся в проекте.

### 3. На 7-8: независимые программы, общая память и именованные семафоры

Сначала откройте два терминала одной Linux/WSL-среды под одним пользователем и перейдите в корень проекта в обоих.

**Терминал 1 - диспетчер:**

```bash
./port_dispatcher examples/manual.txt 100 demo_shm port_shm.log
```

Дождитесь строки READY и списка ACTOR. Для manual.txt в нём пять участников с индексами 0..4. 

**Терминал 2 - участники:**

```bash

./port_tug demo_shm 1 &
./port_berth demo_shm 2 &
./port_crane demo_shm 3 &
./port_warehouse demo_shm 4 &

```

Участники - самостоятельные исполняемые программы; один общий код обмена используется ими повторно.

После подключения последнего начинается моделирование. Если первый терминал показывает ожидание участников, проверьте, что запущен весь список и везде указано одно имя (в примере - demo_shm).

### 4. Выше 8: независимые программы, FIFO и именованные семафоры

Откройте два терминала в корне проекта.

**Терминал 1 - диспетчер:**

```bash
./port_fifo_dispatcher examples/manual.txt 100 demo_fifo port_fifo.log
```

**Терминал 2 - участники после READY:**

```bash
./port_ship demo_fifo 0 &
./port_tug demo_fifo 1 &
```

### Другие конфигурации и аргументы

В manual.txt одно судно, один буксир, один причал и один кран. Для другого конфига число участников и индексы меняются. Нужно смотреть на ACTOR index=... role=... id=... в первом терминале; для каждого индекса запустить программу указанной роли с этой сессией (в примере - demo_shm и demo_fifo). Индекс участника и номер ресурса - разные значения.

Например, для complete.txt нужны команды:

```text
port_ship:      индексы 0, 1, 2
port_tug:       индексы 3, 4
port_berth:     индексы 5, 6
port_crane:     индексы 7, 8
port_warehouse: индекс 9
```

Формат запуска диспетчера:

```text
ПРОГРАММА КОНФИГ [ЗАДЕРЖКА [СЕССИЯ [ЖУРНАЛ]]]
```

- Задержка - 0..1000 мс за тик, по умолчанию 100.
- Сессия - 1..24 латинские буквы, цифры или `_`. Одну сессию одновременно использует один диспетчер. По умолчанию имя создаётся из PID.
- Журнал - обычный файл, по умолчанию port.log.

Универсальный запуск тоже поддерживается:

```bash
./port_sim fork-named examples/manual.txt 100
./port_sim fork-unnamed examples/manual.txt 100
./port_sim shm examples/manual.txt 100 demo_shm port_shm.log
./port_sim fifo examples/manual.txt 100 demo_fifo port_fifo.log
./port_sim config.txt 100
```

Короткая последняя форма использует fork-named. Для shm/fifo после универсального запуска участники запускаются во втором терминале так же, как выше. Исходный config.txt задаёт 25 тиков.

## Полный формат конфигурации

Файл содержит только десятичные целые числа и необязательное слово EXT. Числа разделяются любыми пробельными символами: одной строкой или по одному в строке. Комментарии, знаки перед числами, дроби и экспоненты не поддерживаются. Файл должен быть обычным текстовым файлом до 65535 байт, без нулевых байтов.

### Основные параметры

Первые девять чисел идут строго в таком порядке:

```text
maxTime tugCount berthCount craneCount warehouseCapacity enterExitTime cargoTime shipCount seed
```

| Позиция | Параметр | Допустимое значение |
|---|---|---|
| 1 | maxTime | 0..1000000 тиков; 0 - без ограничения времени |
| 2 | tugCount | 0..16 буксиров |
| 3 | berthCount | 0..16 причалов |
| 4 | craneCount | 0..16 кранов |
| 5 | warehouseCapacity | 1..1000000 единиц вместимости |
| 6 | enterExitTime | 1..10000 - базовая длительность входа/выхода |
| 7 | cargoTime | 1..10000 - базовая длительность грузовой порции |
| 8 | shipCount | 0..32 судна |
| 9 | seed | 0..1000000 - начальное состояние генератора задержек |

Для буксировки и грузовой порции длительность составляет base..base+base/5 включительно. Швартовка длится ровно moorTime. Seed воспроизводит последовательность генератора; PID и автоматически выбранная сессия от него не зависят.

### Причалы

Далее идут **berthCount описаний причалов**, каждое из четырёх чисел:

```text
id small medium large
```

ID - 0..berthCount-1, без повторов. Последние три числа - 0 или 1: разрешены маленькие, средние и большие суда. Например, `0 1 1 0` - причал №0 принимает маленькие и средние суда.

### Краны

Затем craneCount описаний:

```text
id container liquid
```

ID - 0..craneCount-1, без повторов. Последние два числа - 0 или 1: совместимость с контейнерным и жидким грузом. Например, `0 1 0` - кран №0 обрабатывает только контейнерный груз.

### Суда

Затем shipCount описаний:

```text
shipType cargoType volume arrivalTime
```

- shipType: 0 - маленькое, 1 - среднее, 2 - большое судно.
- cargoType: 0 - контейнерный, 1 - жидкий груз.
- volume: 0..1000000 единиц требуемой обработки.
- arrivalTime: 0..1000000 тиков.

ID судов определяются порядком описаний, начиная с 0. При нулевом объёме грузовая стадия пропускается, но вход, причал и выход остаются.

Полный минимальный пример - содержимое manual.txt:

```text
100 1 1 1 10 2 3 1 7
0 1 1 1
0 1 1
0 0 8 0
```

Это 100 тиков, по одному ресурсу, склад на 10, буксировка 2 тика, грузовая порция 3 тика, одно маленькое судно с 8 единицами контейнерного груза в тик 0; seed=7.

### Значения без EXT

Если файл заканчивается после судов:

| Параметр | Значение по умолчанию |
|---|---|
| strategy | 1 - порядок по прибытию |
| reservation | 0 - по стадиям |
| moorTime | 1 тик |
| warehousePeriod | cargoTime |
| warehouseOut | capacity/4+1 за действие склада |
| cargoMask | 3 - оба типа груза |
| Начальные запасы | 0 для обоих типов |
| Подвоз | 0 для обоих типов |
| Маска каждого буксира | 7 - все типы судов |
| Производительность каждого крана | warehouseCapacity единиц за порцию |
| Операция каждого судна | 0 - разгрузка |
| Число кранов каждому судну | 1 |

### Расширение EXT: точный порядок

После судов укажите EXT и **все** следующие параметры. Частичное расширение не допускается.

Сначала десять чисел:

```text
EXT
strategy reservation moorTime warehousePeriod warehouseOut cargoMask initialContainer initialLiquid supplyContainer supplyLiquid
```

| Позиция после EXT | Параметр | Значение |
|---|---|---|
| 1 | strategy | 0 - ID; 1 - прибытие; 2 - меньший остаток |
| 2 | reservation | 0 - стадии; 1 - причал и входной буксир вместе |
| 3 | moorTime | 1..10000 тиков на швартовку/освобождение для ожидания |
| 4 | warehousePeriod | 1..10000 тиков между действиями склада |
| 5 | warehouseOut | 0..1000000 единиц максимального вывоза за действие |
| 6 | cargoMask | 1 - контейнеры; 2 - жидкость; 3 - оба |
| 7 | initialContainer | 0..1000000 контейнерного груза изначально |
| 8 | initialLiquid | 0..1000000 жидкого груза изначально |
| 9 | supplyContainer | 0..1000000 контейнерного груза максимального подвоза за действие |
| 10 | supplyLiquid | 0..1000000 жидкого груза максимального подвоза за действие |

Сумма начальных запасов не превышает warehouseCapacity. Нельзя задавать запас или подвоз типа, запрещённого cargoMask. При работе склад сначала вывозит готовый груз, затем подвозит в пределах свободной ёмкости; контейнерный тип рассматривается раньше жидкого. Ещё не завершённые разгрузки не вывозятся.

После этих десяти чисел:

1. **tugCount масок буксиров**, по одной каждому буксиру в порядке ID. Значение 0..7: бит 1 разрешает маленькие суда, 2 - средние, 4 - большие. Например, 5 означает маленькие и большие, 7 - все, 0 - никакие.
2. **craneCount производительностей**, по одной каждому крану в порядке ID: 1..1000000 единиц за одну грузовую порцию. Для набора кранов значения суммируются; порция не больше остатка груза и доступной складской порции.
3. **shipCount пар** в порядке ID судов:

```text
operation cranesNeeded
```

operation: 0 - разгрузка, 1 - погрузка. cranesNeeded: 1..16. Нехватка совместимых кранов означает ожидание. Груз учитывается один раз за общую порцию после ответов всех кранов.

При разгрузке место сначала учитывается в reserved, а после завершения становится готовым грузом used/stock. При погрузке запас снимается в начале порции, чтобы другое судно не получило тот же груз; остаток задания уменьшается после завершения. Незавершённая погрузка при прерывании считается находящейся в работе.

### Полный пример EXT с погрузкой двумя кранами

```text
300 2 2 2 40 2 4 2 42
0 1 1 1
1 1 1 1
0 1 1
1 1 1
0 0 35 0
2 1 20 0
EXT
1 1 2 5 0 3 10 0 10 10
1 4
5 5
1 2
1 2
```

- Два буксира, два причала, два крана, склад на 40 и два судна.
- Первое судно маленькое, ему нужно погрузить 35 единиц контейнеров; второе большое, ему нужно погрузить 20 единиц жидкости.
- strategy=1, reservation=1, швартовка 2 тика, склад действует каждые 5 тиков.
- Вывоза нет; склад принимает оба типа, изначально есть 10 контейнерных единиц, жидкости нет.
- Подвозится до 10 единиц каждого типа за действие, насколько позволяет свободное место.
- Первый буксир подходит только маленьким судам, второй - только большим.
- Производительность каждого крана - 5; каждому судну нужно по два крана.

Тот же набор чисел содержится в examples/loading_multi.txt. Внутри конфигурационного файла нельзя добавлять подписи и строки с `#` из пояснений.

### Некорректные и невыполнимые данные

Буквы вместо числа, знак, переполнение, повтор ID, неверная совместимость, обрезка EXT и бинарные байты отклоняются до запуска участников. Диагностика показывает путь, строку рядом с ошибкой и причину.

Корректный файл с нулём буксиров или несовместимым оборудованием допускается: недоступный ресурс не появляется автоматически. Такой сценарий фиксирует ожидание по времени или прерывается пользователем. При maxTime=0 он может ждать сигнала.

## Вывод и завершение

События добавляются строками с модельным временем, ID судна и ресурсами. Отображаются прибытие, запрос, назначение, вход, швартовка, складское ожидание, обработка порций, освобождение и отход. Терминал и журнал содержат одинаковые строки.

Основные поля: used - размещённый груз; reserved - место под незавершённые разгрузки; capacity - ёмкость; remaining - ещё не завершённый груз судна. Всегда должно быть used+reserved<=capacity.

В конце появляется строка:

```text
Проверка ограничений ресурсов: пройдена
```

Она означает проверку постоянных правил: склад не переполнен, владельцы ресурсов согласованы, назначения совместимы, отошедшее судно обработано и освободило оборудование.

Итог FINAL: arrived/departed - прибыло/отошло; pending - не завершили цикл, включая ещё не прибывшие; partial - частично обработаны; cargo_operations - завершённые порции; moved - завершённый объём; wait - ожидание в тиках; max_queue - максимальная очередь.

Три штатных варианта завершения:

1. Все суда отошли: `Termination: all ships processed`.
2. Достигнут maxTime: `Termination: simulation time limit`. Выводятся стадии и остатки незавершённых судов.
3. Ctrl+C/SIGINT или SIGTERM: `Termination: Interrupted by user signal`. Формируется итог, участники останавливаются, дочерние процессы забираются waitpid, созданные объекты обмена удаляются.

Коды выхода: 0 - штатный итог; 2 - неверный ввод; 3 - ошибка запуска, участника, протокола, ограничений или вывода. 

## Тесты

```bash
make test
```

Makefile собирает приложение и port_tests из tests/test_port.c и tests/test_support.c. Затем C-программа напрямую запускает проверяемые программы через fork/exec, проверяет строки, коды, сигналы и очистку.

Запускайте тесты из корня проекта. Проверяются: штатная работа, погрузка несколькими кранами, стратегии, совместимость, пустые суда, горизонт, частичная обработка, максимальное число участников и прибытие через миллион тиков. Дополнительно проверяются сигналы, повтор сессии, неправильная роль, падение участника.

Есть проверки неверных чисел, типов, границ, ID, EXT, размера файла, NUL.

### Проверка памяти

```bash
make sanitize
ASAN_OPTIONS=detect_leaks=1:halt_on_error=1:quarantine_size_mb=32 UBSAN_OPTIONS=halt_on_error=1 ./port_tests
make clean
make
```
Санитайзеры ищут ошибки памяти и UB.

## Консольная панель

В обычном терминале автоматически появляется панель `ARKHANGELSK BAKARITSA PORT`: время, ресурсы, склад, суда и последние 8 событий. `*` отмечает занятый буксир, `#` - занятый причал, `^` - занятый кран; отсутствие символа означает свободный ресурс. У судна показаны оставшийся объём, состояние и операция `load`/`unload`. У склада отдельно показано зарезервированное место: проверяется сумма `used + reserved`, а не только видимое количество готового груза.
